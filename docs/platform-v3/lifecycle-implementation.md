# Lifecycle implementation and host API

Record: TASK-V3-001; requirements REQ-V3-001–009, NFR-V3-001–005; design DES-V3-001 / CR-V3-001. Implementation evidence is developer verification, not independent acceptance or a project Gate decision.

The existing `Runtime.execute` facade routes additive lifecycle commands in the same transaction as the existing request cache. V2 commands and `snapshot()` retain their contracts. `Store` adds `lc_*` tables without changing V2 columns or journal mode. Migration 1 has a persisted SHA-256 and must never be edited after application; later schema changes require another migration. Structured entity JSON is indexed by project/status/id, with extra active lease, active execution, event sequence and trace endpoint indexes. Artifact/case/release definitions have separate immutable version records. Evidence, assessments, decisions and events are append-only through the API.

## Minimal host setup

```python
from rd_platform.runtime import Runtime
r = Runtime('.rd-platform/state.db')
# Use an existing V2 project ID and actual registered host agent identity.
r.execute('lifecycle.initialize', {
    'project_id': project_id, 'repository_root': repository_root, 'mode': 'active'
})
r.execute('artifact.create', {
    'project_id': project_id, 'artifact_type': 'REQ', 'artifact_id': 'REQ-001',
    'title': 'Measurable requirement', 'state': 'BASELINED',
    'content_ref': {'inline_json': {'acceptance': 'observable criterion'}},
    'source': {'kind': 'host', 'actor': actual_agent_id}
})
r.lifecycle_snapshot(project_id, after_sequence=0, limit=200)
```

All references normalize to `{type, id, version}`; omitted version locks the currently registered version. Artifact types are BG/MR/PRD/REQ/NFR/DES/ADR/TASK/CODE_CHANGE/CR/RISK/DOC/TEST_MODEL, with CODE- and TM- prefixes for the latter special names. Test models are created through `test_model.create` with TM- IDs; their TEST_MODEL references resolve the model registry. Case IDs use TC-, defects BUG-, releases REL-, evidence EVD-. IDs are globally unique within their entity table and cannot be reused. Cross-project references, wrong types, stale versions, malformed/non-finite JSON and duplicate references are rejected.

Content is exactly one of `{inline_json: value}` or `{path: repository_relative_path, sha256: expected_sha256}`. Inline content is limited to 1 MiB and its digest is computed. A file must exist, resolve beneath the initialized repository, have no `..` component and match the caller's digest. This API registers existing repository files; it never overwrites an artifact file. Callers persist a new Git file/version before registration. Changing a registered file without registering a revision makes its references unusable. Sensitive field names require `[REDACTED_SECRET]` or `secret-ref:...`; callers remain responsible for not embedding secrets in free-form prose.

## Commands and evidence

Commands: `lifecycle.initialize/control`, `artifact.create/revise`, `evidence.register`, `trace.link/invalidate`, `test_model.create`, `test_case.create/revise`, `test_execution.start/finish`, `defect.classify/fix/resolve/close`, `gate.assess/decide`, `release.create/ready/record_deployment/rollback`, `work.create/claim/heartbeat/finish/control/reap`.

`evidence.register` takes `project_id`, optional `evidence_id`, `kind`, `status`, `source:{kind,actor}`, `locator` in the content format above, timezone-aware non-future `observed_at`, and `metadata`. Source kinds are host/tool/import/model. VERIFIED is permitted only for host/tool provenance; the actor must already be a registered agent. `metadata.artifact_refs` locks the actual subject versions. New evidence may specify `supersedes_id`; superseded evidence cannot satisfy a current verification. Evidence registration records a host-attested fact, not an independently executed command. Actual command execution is the CLI/harness responsibility.

For execution evidence use kind `test_execution`, a tester actor and metadata `{execution_id, result, artifact_refs:[{type:'TEST_CASE',id,version}]}`. A PASS/FAIL execution requires matching verified tester evidence recorded after execution start. The optional V2 quality run must remain ACTIVE/current. BLOCKED/NOT_EXECUTED retains the actual reason and never creates a passing result. Performance/stress/stability executions require actual sample count, positive duration, load model and raw-result locator.

Test models require a function tree, requirements, objects `{object_id,description}`, risks `{risk_id,description,likelihood,impact,priority,requirement_refs}` and points `{point_id,object_id,type,rationale,risk_refs,requirement_refs,coverage_rule}`. Likelihood/impact are LOW/MEDIUM/HIGH and priority P0–P3. A case must reference an existing point and intersect its requirements. Its ordered steps, data, preconditions, expected result and automation are versioned. `test_case.revise` merges an updated complete definition with the previous one using `expected_version` and `reason`.

FAIL atomically opens an UNCLASSIFIED defect. Classification requires `classified_by` tester/reviewer, category/severity/owner_role/rationale/evidence_refs. `defect.fix` requires the classified owner as `fixed_by`, a same-project BASELINED/APPROVED TASK artifact `fix_task_id`, verified evidence and `completion_task_id`. The TASK's structured JSON content must contain `{defect_id,requirement_refs,quality_task_id}`. That quality task must be a real V2 DONE task created after the defect, whose inputs bind `{fix_defect_id,lifecycle_task_ref:{type:'TASK',id,version}}` and whose current implementation/unit/integration/review runs all PASS with distinct developer/tester/reviewer identities. REQUIREMENT defects also require `change_id`. The fix snapshots quality task revision/attempt and computes a regression set of cases sharing affected requirements. `defect.resolve` requires a distinct tester `resolved_by` and `execution_refs` covering the entire current set with fresh PASS results after the fix. `defect.close` requires a separate reviewer `closed_by`, fresh `review` evidence with `{subject_id:bug_id,result:'PASS',artifact_refs}`, and still-current passing regression results. Resolve and close revalidate the immutable TASK content hash, scope and current completed quality chain. The original failed execution remains immutable history.

## Gate and release policy

Current adapter update (CR-V3-003/004): [SSH approval provider](approval-provider.md), [worker service](worker-service.md), and [deployment executor](deployment-executor.md) are now bundled as opt-in trusted-host adapters. Default approval remains unavailable until a real trust configuration is supplied. The Runtime domain APIs below record/validate facts; the separate adapters perform external execution. Earlier developer verification counts at the end remain historical observations.

`lifecycle_governance.POLICY` lists every G0–G11 criterion. Criterion evidence metadata has `{gate_id,criteria:[...],artifact_refs:[...]}`. Document criteria require verified document/review/environment evidence against BASELINED/APPROVED current artifacts. Test criteria require tester execution evidence linked to a finished PASS execution; review criteria require reviewer `review` evidence with result PASS. G7 onward also requires complete trace and current passing cases, and blocks unresolved UNCLASSIFIED/BLOCKER/CRITICAL defects. G10 needs a release manifest; G11 needs an actual RELEASED deployment record. All preceding Gates must have PASS decisions.

`gate.assess` produces an immutable candidate/checks/missing/input-digest record. `gate.decide` requires the current assessment and role reviewer (G10 also permits release_manager). PASS needs qualified `gate_decision` evidence metadata `{assessment_id,status:'PASS'}` recorded by `decided_by`. FAIL/BLOCKED requires `reason` and `resolution`; FAIL additionally creates a remediation work order. Decisions and histories survive invalidation. Revising a subject invalidates outgoing downstream links/cases/work, affected assessments, subsequent Gate decisions as current decisions, and referenced releases; unrelated branches stay current. Material artifact revisions default to requiring a same-project CR; an explicit `material:false` is for nonmaterial revisions.

G9–G11 additionally require human approval. `execute('evidence.register',...)` categorically rejects human_approval. `Runtime.register_human_approval(data,operator=...)` fails with `human approval provider NOT_AVAILABLE` by default. A host must explicitly construct `Runtime(db,approval_provider=provider)` with a real authentication adapter, such as the bundled opt-in SSH provider; no operator credentials or actual human approval are bundled. The provider implements `verify(binding=...,approval_request=...)` and must return `{authenticated:true,operator,provider_id,verification_id,binding_digest}`. The authenticated operator must match the claimed hint and cannot be a registered agent. The immutable verification binding covers project, Gate, decision, statement, subject versions/content digests, policy version and current policy input digest. Wrong bindings and reused provider verification IDs are rejected; Gate evaluation rechecks current binding. The request remains kind human_approval/status VERIFIED, locator/observed_at, and metadata `{gate_id,decision:'APPROVE'|'REJECT',statement,artifact_refs}`. This channel is absent from HTTP and generic worker command dispatch. Only temporary-db tests inject `SyntheticApprovalVerifier`; that proves verification mechanics and is never evidence of an authenticated real human.

Release creation locks artifacts, requirements, known BUG/RISK refs and a DOC rollback_ref. READY requires a current G10 PASS and decision evidence. Explicit operator deployment recording requires fresh release_manager `deployment` evidence matching release/result plus `deployment_environment` evidence. A release stays DEPLOYMENT_FAILED on FAIL. Rollback requires a prior deployment fact, reason/operator/result and fresh matching `rollback` evidence; it preserves the original deployment and adds ROLLED_BACK/ROLLBACK_FAILED. The API records verified external actions; it does not execute deployments or assert customer acceptance.

## Host work and recovery

Work creation requires gate/activity/required_role/why/input_refs/dependencies and output_contract `{required_types:[],min_outputs:1}`. Dependencies must belong to the same project. Claim requires the matching registered role, all dependencies DONE, current inputs, and 1–3600 lease_seconds. The handoff includes activity, reason, inputs, contract, attempt and version; only the first claim response includes the random lease_token. Storage retains its SHA-256. Heartbeat extends the current lease. Finish requires a current lease and DONE/FAILED/WAITING_USER/BLOCKED; DONE validates referenced outputs against the contract. Worker completion is not a Gate PASS.

Pause invalidates active tokens and stops claims; resume permits fresh claims. This does not kill an external process. `work.reap` reclaims expired leases and records the event; claim also reaps expired project leases. Old host results are rejected. `work.control` supports retry/reject/modify/reassign/skip/rollback with reason, invalidates dependent work, and preserves history. Retry is bounded to three attempts. Modify takes refreshed input_refs; reassign requires a matching agent; rollback creates a compensation work order. `lifecycle.control` also supports rollback with `target_gate`, `change_id`, `affected_refs`, and reason. The target must be strictly earlier than the current Gate. It preserves artifact versions and original decisions, marks affected assessment freshness SUPERSEDED, invalidates target/downstream Gate state and creates a compensation work order. Actual environment rollback remains a separate evidence-backed external operation.

Request IDs retain normal transactional idempotency. A repeated `work.claim` request for the same current agent/attempt/version immediately rotates the random lease token and appends `work.lease_reissued`. The retry receives a usable token even when the first response was lost, and every earlier token is invalid. Changed/invalidated attempts cannot be resurrected with an old request. The request cache and work record never store the raw token; heartbeat/finish request payloads store only token hashes. No raw token appears in snapshots or events.

Gate snapshots re-evaluate current evidence and content hashes before showing cached PASS. A stale Gate and its downstream Gates project `gate_status:null`, `evaluation_state:NOT_EVALUATED`, `freshness:STALE`, with the original `recorded_gate_status` and decision history retained. This is a read-only validity projection, not a new Gate decision. The lifecycle current Gate and next actions point to the earliest stale evidence. Assessment/decision/release operations also re-evaluate preceding Gate evidence; an old PASS cannot authorize later work after path-backed evidence drift. Evidence registration rejects bearer/basic credentials, password/API-key/header assignments, private-key blocks and known environment secrets inside text values; snapshot/event projections additionally redact historical text. Arbitrary confidential prose still requires caller discipline.

Snapshots return gates/work/artifacts/trace/models/cases/executions/defects/assessments/decisions/evidence/releases and bounded event pages. `next_sequence/has_more` page events; entity lists are capped at limit and `collection_counts/collections_truncated` disclose truncation. Entity cursor paging is implemented in `lifecycle_collection`. `lifecycle-report` now reads all entity pages in one consistent read transaction, including more than 500 cases/executions; `project-export` publishes a separate read-only project document projection. See [project export](project-export.md). The 100-project/100k-artifact/1M-event synthetic read-capacity target has been measured; see [actual metrics and workload boundaries](performance-validation.md). Evaluations and requirement summaries currently traverse project records in Python.
